# SurfingStudio 协作规范（提交 / Issue / 版本命名）

> 适用范围：本仓库的 Git 分支、GitHub 提交信息、Issue 与版本发布。
> 与 [代码规范](./代码规范.md) 配套：代码规范规定“怎么写代码”，本文档规定“怎么提交、怎么记录问题、怎么编号发布”。
>
> 约定级别：
> - **必须**：违反会导致历史不可追溯或发布版本不可复现，Review 应直接拒绝。
> - **应当**：默认遵守；确有理由时需在提交说明或 Issue 中解释。
> - **可以**：可选建议。

1. 分支模型

4. 版本命名规范

- [项目简介](./项目简介.md)：用户可见功能与版本能力说明。

- `history/ai/`：AI 生成或修改代码后的变更记录（见代码规范 10.7）。

## 1. 分支模型

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 只保存已发布的正式版 | 只能通过发布流程合入；每个正式版在 `main` 上打 tag |
| `test` | 下一版本的集成分支 | 从 `main` 最新正式版拉出；日常修改、构建、私密测试与对外测试都在这里进行 |
| `feature/<slug>` | 单个功能开发 | 从 `test` 拉出，完成后合回 `test`；`slug` 为小写英文 kebab-case |
| `fix/<slug>` | 单个缺陷修复 | 从 `test` 拉出（影响已发布版本的缺陷从 `main` 拉出，见 4.6） |
| `hotfix/<slug>` | 正式版紧急修复 | 从对应正式版 tag 拉出，修复后按 4.6 递增版本号发布 |

- **必须**：功能与修复不直接提交到 `main`。
- **必须**：分支名与关联 Issue 在 Issue 中互相登记（分支名写入 Issue，Issue 号写入提交脚注）。
- **应当**：分支生命周期尽量短；合入 `test` 前先同步 `test` 最新代码。

## 2. 提交规范

### 2.1 提交粒度

- **必须**：一次提交只做一件事。功能、重构、格式化、依赖升级不得混在同一次提交中。
- **必须**：代码改动与对应文档更新（[技术文档](./技术文档.md)、[关键常量](./关键常量.md)、[框架工作流](./框架工作流.md)、[项目简介](./项目简介.md)）放在同一次提交。
- **必须**：使用 AI 生成或修改代码时，`history/ai/YYYYMMDD-HHmmss-<task-slug>.md` 与代码在同一次提交中提交。
- **必须**：提交前代码可编译，`cargo fmt` 已执行，`cargo test` 通过。
- **禁止**：提交 `target/`、日志文件（`.sflog` / `.txt` 调试输出）、本机路径配置、临时脚本与实验文件。

### 2.2 提交信息格式

采用 Conventional Commits，结构**必须**为：

```text
<type>(<scope>): <简短描述>

<正文：为什么改、改了什么、影响范围；可省略>

<脚注：BREAKING CHANGE / Closes #12 / Refs #34；可省略>
```

- `type`、`scope` 使用英文小写；`简短描述` 使用中文，不加句号，不超过 50 个字符。
- 标题与正文之间空一行；正文每行不超过 72 个字符。
- 一条提交只写一个 `type`；确实包含多种改动时拆成多条提交。

### 2.3 type 取值

| type | 用途 |
| --- | --- |
| `feat` | 新增用户可见功能 |
| `fix` | 修复缺陷 |
| `perf` | 性能优化（不改变外部行为） |
| `refactor` | 重构（不新增功能、不修缺陷） |
| `docs` | 仅文档改动（含 README、`doc/`、`history/`） |
| `test` | 仅测试代码改动 |
| `build` | 构建系统、依赖、打包脚本、`Cargo.toml` |
| `ci` | CI / 自动化流程改动 |
| `style` | 纯格式化，不改变逻辑 |
| `chore` | 杂项维护（清理、注释、忽略文件） |
| `revert` | 回滚既有提交，正文必须写明被回滚的 commit |

### 2.4 scope 取值

scope 表示受影响的一层或一个子系统，优先使用模块名：

| scope | 对应位置 |
| --- | --- |
| `core` | `src/core/`（模型、工程运行时、MIDI 输入） |
| `audio` | `src/audio/`（引擎、乐器、效果器、I/O、ASIO、GPU） |
| `plugin` | `src/plugin/`（插件宿主与 VST3 / VST2 后端） |
| `platform` | `src/platform/`、`platforms/` |
| `app` | `src/app/`（状态机、多窗口、文件与设置） |
| `ui` | `src/ui/`（编曲区、卷帘、检查器、主题） |
| `diag` | `src/diag/`（诊断日志） |
| `android` | 安卓入口、清单与打包脚本 |
| `docs` | `doc/`、`README.md`、`history/` |
| `build` | `Cargo.toml`、`vendor/`、`tools/` |
| `release` | 版本号、tag 与发布说明 |

- 跨多个 scope 的提交**应当**拆分为多条；确实无法拆分时可省略 scope，或使用主 scope。
- 不允许自造 scope 名称；确需新增时先在本表登记。

### 2.5 脚注规则

| 场景 | 写法 |
| --- | --- |
| 关闭 Issue | `Closes #12`（修复类提交必须写；无 Issue 时先建 Issue） |
| 关联但未关闭 | `Refs #34` |
| 破坏性变更 | `BREAKING CHANGE: <不兼容点与迁移方式>`（工程格式不兼容时必须写） |
| 回滚 | `Reverts <commit>` |

### 2.6 示例

```text
feat(ui): 钢琴卷帘底部增加力度控制器开关

力度视图默认关闭，避免窄窗口挤压音符区。开关状态按轨道保存在 UI 状态中，
不写入工程文件。

Closes #21
```

```text
fix(plugin): 修复 Kontakt 8 附加后才可查询编辑器尺寸导致的打开卡顿

窗口先以占位尺寸创建，attach 后再按插件声明尺寸调整。

Closes #37
```

```text
docs(docs): 新增协作规范，声明提交、Issue 与版本命名规则
```

### 2.7 禁止事项

- **禁止**：`update`、`fix bug`、`修改一下`、`提交` 等无法说明改动的标题。
- **禁止**：同一提交同时包含代码与无关文档重排、全文件格式化。
- **禁止**：改写已合入 `main` 或已打 tag 的历史；需要纠正时新增 `revert` 提交。
- **禁止**：`--no-verify` 跳过提交检查（确需跳过时必须在提交正文说明原因）。

### 2.8 禁止提交的文件

仓库根目录的 `.gitignore` 是本文档的落地实现；新增或修改忽略项时**必须**同步更新本节。

| 类别 | 典型文件 | 原因 | `.gitignore` 规则 |
| --- | --- | --- | --- |
| 构建产物与缓存 | `target/`、`*.pdb` | 可由源码重建，体积大且随本机变化 | `/target/`、`*.pdb` |
| 诊断日志 | `*.sflog`、`diag_*.log`、解码后的 `.txt` | 含本机路径、插件与设备信息，属于运行期数据 | `*.sflog`、`*.log` |
| 调试输出与截图 | `crash_log.txt`、`out_dbg.txt`、`.screenshots/` | 一次性排查素材，容易泄漏本机信息 | 对应文件名、`/.screenshots/` |
| 自动保存与历史版本 | `*.autosave.sfsd`、`Backups/` | 崩溃恢复文件与本机备份，不属于源码 | `*.autosave.sfsd`、`Backups/` |
| 本机设置与缓存 | `settings.json`、`plugin-cache.json` | 保存用户目录与本机插件路径 | `/settings.json`、`/plugin-cache.json` |
| 签名文件与密钥 | `*.keystore`、`*.jks`、`*.p12`、`local.properties` | 泄漏后无法撤回，且会导致签名被冒用 | 对应扩展名 |
| 安卓构建产物 | `*.apk`、`*.aab`、`*.idsig` | 由源码打包，发布产物走 Release | 对应扩展名 |
| 第三方音频素材 | `examples/**/Data/*.wav`、`*.mp3` 等 | 体积大（范例中单个文件接近 100 MB）且版权不明 | `examples/**/Data/*.{wav,mp3,flac,aiff,ogg,m4a}` |
| IDE / 操作系统文件 | `.idea/`、`.vscode/`、`.DS_Store`、`Thumbs.db` | 个人配置，与项目无关 | 对应目录与文件名 |
| 本地环境变量 | `.env`、`.env.*` | 可能含密钥与个人路径 | 对应文件名 |

补充规则：

- **必须**：范例工程只提交 `.sfsd` / `.sndp` / `comp.dat` 等工程文件；涉及的大体积媒体（WAV / MP3）不入库，由使用者自备，或在 Issue / Release 中另行提供。
- **必须**：单文件超过 50 MB 不得直接提交；确需入库时改用 Git LFS，并在本节登记规则与用途。
- **禁止**：`git add -A` / `git add .` 盲加全部文件；提交前先看 `git status`，按文件名逐个添加。
- **禁止**：提交个人绝对路径、真实姓名目录、内网地址与测试用的第三方插件二进制。

**检查与纠错**

```bash
git status --short --ignored     # 确认待提交列表与已忽略项
git check-ignore -v <路径>       # 查某个文件为何被忽略
git rm --cached <路径>           # 已误加入暂存区：从索引移除，保留本地文件
```

- 误提交且尚未推送：撤销该提交后重新提交。
- 已推送：**禁止**强推改写公开历史；直接 `git rm --cached` 后补一条 `chore(build): 移除误提交文件` 提交，并评估是否需要更换被泄漏的密钥。

## 3. Issue 规范

### 3.1 Issue 类型与标题

标题格式**必须**为 `[类型] 简短描述`，类型取值：

| 类型 | 用途 |
| --- | --- |
| `[Bug]` | 缺陷、崩溃、输出异常、卡顿 |
| `[Feature]` | 新功能或功能增强 |
| `[Task]` | 重构、文档、构建、发布等内部工作 |
| `[Question]` | 使用疑问与讨论，可转为 Bug 或 Feature |

- 描述使用中文，点明现象或目标，不超过 60 个字符。
- 示例：`[Bug] 播放中打开 Kontakt 编辑器导致音频欠载`、`[Feature] 控制器卷帘支持复制到其他轨道`。

### 3.2 `[Bug]` 必填字段

```markdown
## 环境
- 版本：1.1.2t / 1.1.2a / 1.1.2（填写实际构建号与后缀）
- 系统：Windows 11 23H2
- 音频：WASAPI / ASIO（驱动名称）、采样率与缓冲
- 插件：涉及的 VST3 / VST2 名称与版本

## 复现步骤
1. …
2. …

## 期望行为
…

## 实际行为
…（含崩溃信息、错误提示原文）

## 日志
- 现象发生时间与 `.sflog` 文件名（位于 `%LOCALAPPDATA%\SurfingStudio\logs`）
- 可用 `surfing-studio.exe --decode-log <文件>` 解码后附上相关片段

## 影响范围
是否稳定复现、影响的工程/轨道、是否只在特定插件下出现
```

- **必须**：写明版本号与后缀。缺版本号的 Issue 无法定位构建，维护者**应当**要求补充后再处理。
- **应当**：附上最小复现工程（`.sfsd`）或可公开的示例；涉及插件时说明插件是否为必需条件。

### 3.3 `[Feature]` / `[Task]` 必填字段

```markdown
## 背景与目标
要解决什么问题、面向哪类使用场景

## 期望行为 / 交付物
用户可见的表现，或需要产出的文档、脚本、配置

## 影响模块
core / audio / plugin / platform / app / ui / diag / docs

## 验收标准
- [ ] 可验证的条件 1
- [ ] 可验证的条件 2

## 可选方案（可省略）
```

### 3.4 标签

至少包含 1 个类型标签；其余按需添加：

| 维度 | 标签 |
| --- | --- |
| 类型 | `type/bug`、`type/feature`、`type/task`、`type/question` |
| 优先级 | `P0`（崩溃/数据丢失）、`P1`（主要功能不可用）、`P2`（一般缺陷）、`P3`（体验与建议） |
| 状态 | `status/triage`、`status/doing`、`status/testing`、`status/done`、`status/wontfix` |
| 模块 | `area/core`、`area/audio`、`area/plugin`、`area/app`、`area/ui`、`area/diag`、`area/platform`、`area/android`、`area/docs` |

### 3.5 生命周期

```text
新建 → status/triage（确认与去重） → status/doing（关联分支） → status/testing（已有构建号）
     → status/done（进入 t 版或正式版） → 关闭
```

- `status/doing` 时**必须**在 Issue 中登记分支名；提交时用 `Closes #id` 关联。
- `status/testing` 时**必须**在 Issue 中写明验证用的构建号（`x.y.za` 或 `x.y.zt`）。
- **关闭条件**：修复已合入 `test` 并通过私密测试，或功能验收标准全部满足；关闭时补一条说明，写明关联提交（commit）与首次包含该修复的版本号。
- **禁止**：无说明直接关闭；不修复时**必须**改为 `status/wontfix` 并写明原因与替代方案。
- 同一问题再次出现时**必须**重新开启原 Issue（或新建并 `Refs` 原 Issue），不得静默忽略。

## 4. 版本命名规范

### 4.1 版本号结构

```text
<大版本>.<小版本>.<小版本构建修改数>[后缀]
```

- **大版本**：发生工程文件不兼容、架构级重写或对外行为破坏性变更时递增，从 `1` 起。
- **小版本**：一个发布周期（`test` 分支的开发目标）递增一次，表示本周期以 `main` 上的某个正式版为基线、目标发布的下一个功能版本。
- **小版本构建修改数**：本周期内每次产生新的构建产物递增一次，首个构建为 `0`。
- **后缀**：
  - `a`：构建版本，仅用于内部私密测试，不对外发布；
  - `t`：对外测试版；
  - 无后缀：正式版。

版本号中不出现 `v` 前缀；`v` 只用于 Git tag（见 4.6）。

### 4.2 三个阶段

| 阶段 | 版本示例 | 含义 | 对外 |
| --- | --- | --- | --- |
| 构建版 | `1.1.2a` | `test` 分支上的第 3 次构建，供内部私密测试 | 否 |
| 对外测试版 | `1.1.2t` | 与 `1.1.2a` 同号、私密测试通过后发布 | 是 |
| 正式版 | `1.1.2` | 与 `1.1.2t` 同号、对外测试无问题后发布 | 是 |

- `a → t`、`t → 正式版` 只改变后缀，**不改变**版本号数字。
- 只有通过私密测试的构建才能发布为同号 `t`；未通过的构建不得对外发布。
- **必须**：一个对外测试版发现问题后，不得发布同号正式版；继续修改并递增构建修改数，重新走 `a → t → 正式版`。

### 4.3 完整示例（当前 `main` 为 `1.0.0`）

`test` 分支在 `1.0.0` 基础上开发，目标小版本为 `1.1`，构建修改数从 `0` 开始：

```text
main 1.0.0
  └─ test：目标 1.1，构建修改数从 0 开始
       ├─ 第 1 次修改并构建            → 1.1.0a（私密测试未通过）
       ├─ 第 2 次修改并构建            → 1.1.1a（私密测试未通过）
       ├─ 第 3 次修改并构建            → 1.1.2a（私密测试通过）
       │                              → 发布对外测试版 1.1.2t
       │                                   ├─ 测试无问题 → 发布正式版 1.1.2
       │                                   │             → 合入 main，打 tag v1.1.2
       │                                   │             → 下一周期基线 1.1.2
       │                                   └─ 测试发现问题 → 不得发布 1.1.2
       │                                                 → 第 4 次修改并构建 1.1.3a
       │                                                 → 私密测试通过 → 1.1.3t
       │                                                 → 依此类推
```

- 对外测试版号一旦发布，该号即被占用；`1.1.2t` 出问题后只能继续向上递增，**禁止**重新发布修改过的 `1.1.2t`。
- 正式版发布后，`main` 上的版本号即为下一周期的基线，小版本 `+1`、构建修改数归 `0`。

### 4.4 递增规则

| 场景 | 版本动作 | 示例 |
| --- | --- | --- |
| 从 `main` 最新正式版拉出 `test` 开始新周期 | 小版本 `+1`，构建修改数归 `0` | `1.0.0` → 首个构建 `1.1.0a` |
| `test` 上每次修改后重新构建 | 构建修改数 `+1` | `1.1.0a` → `1.1.1a` |
| 私密测试通过 | 后缀 `a` 改为 `t`，数字不变 | `1.1.2a` → `1.1.2t` |
| 对外测试无问题 | 去掉后缀发布正式版，数字不变 | `1.1.2t` → `1.1.2` |
| 对外测试发现问题 | 构建修改数 `+1`，重新从 `a` 开始 | `1.1.2t` → `1.1.3a` → `1.1.3t` |
| 正式版紧急修复（hotfix） | 以该正式版为基线，构建修改数 `+1` | `1.1.2` 修复 → `1.1.3a` → `1.1.3t` → `1.1.3` |
| 工程格式不兼容 / 架构级破坏性变更 | 大版本 `+1`，小版本与构建修改数归 `0` | `1.1.2` → `2.0.0a` |

- **必须**：版本号严格单调递增，不得回退、跳号或复用。
- **禁止**：直接发布未经过 `a` 构建与私密测试的 `t` 版。
- **禁止**：正式版与对应 `t` 版数字不一致（如 `1.1.2t` 发布为 `1.1.3`）。

### 4.5 发布前检查

- [ ] `Cargo.toml` 的 `[package] version` 已更新为本次版本号（带 `a` / `t` 后缀时也写入后缀）。
- [ ] 安卓发布时同步 `platforms/android/AndroidManifest.xml` 的 `android:versionName`，并递增 `android:versionCode`。
- [ ] `cargo build --release` 与 `cargo test` 通过；构建产物版本与登记版本一致。
- [ ] 诊断日志中的版本号（取自 `CARGO_PKG_VERSION`）与发布号一致。
- [ ] 本次包含的 Issue 已关联提交并核对关闭状态。
- [ ] 正式版：`test` 已合入 `main`，并打好 tag。

### 4.6 版本号落地位置

| 位置 | 规则 |
| --- | --- |
| `Cargo.toml` → `[package] version` | 唯一权威版本号，所有构建从这里取值 |
| `platforms/android/AndroidManifest.xml` | `android:versionName` 与主包一致；`android:versionCode` 每次对外发布 `+1` |
| Git tag | `v1.1.2a` / `v1.1.2t` / `v1.1.2`，正式版不加后缀；tag 注释写版本说明与 Issue 列表 |
| 发布说明（Release） | 标题为版本号；正文列新增功能、修复的 Issue、已知问题与升级注意 |
| 提交信息 | 版本号变更单独提交：`build(release): 版本号提升至 1.1.2t` |

- **必须**：改版本号的提交与功能改动分开，便于回滚与按版本检索。
- **应当**：hotfix 发布后同步回合 `test` 分支，避免下一版本重复修复。

## 5. 速查表

| 场景 | 做法 |
| --- | --- |
| 提交代码 | `feat(ui): 简短中文描述` + 正文 + `Closes #12` |
| 提交文档 | `docs(docs): …` |
| 提 Bug | 标题 `[Bug] …`，附版本号、复现步骤、期望/实际与 `.sflog` |
| 提需求 | 标题 `[Feature] …`，附背景、影响模块与验收标准 |
| 开始新周期 | 从 `main` 最新正式版拉 `test`，首个构建 `x.(y+1).0a` |
| 私密测试通过 | `x.y.za` → `x.y.zt` |
| 对外测试通过 | `x.y.zt` → `x.y.z`，合入 `main` 并打 tag `vx.y.z` |
| 对外测试失败 | 继续构建 `x.y.(z+1)a` → `x.y.(z+1)t` |
| 破坏性变更 | 大版本 `+1`，如 `2.0.0a` |
